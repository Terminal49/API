Terminal49 is a direct integration with 36\+ ocean carriers and North American terminals, so the container object carries holds, fees, last free day, and release readiness that most tracking APIs do not expose. If you are running another provider today, this section maps your current integration onto Terminal49, field by field, so you can cut over without reverse-engineering our schema.

Each guide covers the same ground: authentication, request and response mapping, event and webhook equivalents, error handling, gotchas, and a step-by-step migration checklist. There is also an AI coding agent prompt on each page that you can hand to Cursor, Claude Code, or Copilot to run a side-by-side migration.

## What every migration has in common

<Steps>
  <Step title="Self-serve an API key">
    Create a Terminal49 account at [app.terminal49.com](https://app.terminal49.com) and generate a key at [app.terminal49.com/developers/api-keys](https://app.terminal49.com/developers/api-keys). The free Developer Key tracks up to 10 active containers, enough for a parity test.
  </Step>
  <Step title="Register tracking requests once">
    `POST /v2/tracking_requests` per BOL, booking, or container. Terminal49 polls the carrier, terminal, and rail sources on your behalf.
  </Step>
  <Step title="Receive updates via webhook">
    Subscribe to the events you act on. 30\+ webhook events, HMAC-signed, delivered as changes happen. Polling remains available if you prefer.
  </Step>
  <Step title="Wire up the operational fields">
    Holds, fees, last free day, and release readiness come back on the container object wherever the terminal is a supported source. These are the reason to migrate rather than port like for like.
  </Step>
</Steps>

  <Card title="Terminal fees" icon="dollar-sign">

  <Card title="Last free day" icon="calendar-days">
    `pickup_lfd` with per-source breakdown for shipping line, terminal, and rail. Each source has its own webhook event.
  </Card>

  <Card title="Release readiness" icon="circle-check">
    `available_for_pickup` combined with the holds array answers "can I pick this up?" in one call.
  </Card>
</CardGroup>

## The core API shape, once

Regardless of where you are coming from, the Terminal49 request pattern is the same.

```bash Create a tracking request
curl -X POST https://api.terminal49.com/v2/tracking_requests \
  -H "Content-Type: application/vnd.api+json" \
  -H "Authorization: Token YOUR_API_KEY" \
  -d '{
    "data": {
      "type": "tracking_request",
      "attributes": {
        "request_number": "YOUR_BOL_NUMBER",
        "request_type": "bill_of_lading",
        "scac": "MAEU"
      }
    }
  }'
```

<Note>
  Terminal49 uses `Authorization: Token <key>`, not `Bearer`. Content type is `application/vnd.api+json` (JSON:API). Responses include `data`, `relationships`, and an `included` array.
</Note>

# Test execution and runtime comparison, October 21, 2026

Selecting only workspaces in `npm test` removes a duplicate run of the root policy suites. Both policy suites and every workspace test remain. Production continues to use Node 24 and npm.

## Test execution

| Command | Median seconds | Minimum to maximum | Measured trials |
| --- | ---: | ---: | ---: |
| Original recursive selection | 58.947 | 58.645 to 59.565 | 5 |
| Explicit workspace directories | 38.463 | 37.522 to 39.812 | 5 |

Median wall time fell by 34.75%, and median child CPU time fell by 33.96%. The original command ran policy suites with 99 and 50 tests twice. The revised command runs them once alongside all 1,316 workspace tests, preserving all 1,465 unique tests in the measured snapshot. This removes duplicate work; it does not accelerate each test or establish production request latency.

These measurements use public source commit `80e227ec2402f72a86778a2b76cb82b761576009`, before subsequent application changes. The selection fix has been rebased onto current main; its current correctness verification is separate from this historical timing snapshot.

## Runtime observations

Five measured rotating trials and one excluded warmup ran per runtime and workload. CLI values are per-launch means within ten-launch samples. The SDK used the existing Vitest suite. The synthetic Model Context Protocol (MCP) loop lists tools and reads one fixture container thirty times.

| Runtime | SDK suite, seconds | CLI startup, milliseconds | MCP client plus handler loop, seconds |
| --- | ---: | ---: | ---: |
| Node 24.22.1 | 3.590 | 73.209 | 3.559 |
| Node 26.12.1 | 3.580 | 71.019 | 3.357 |
| Bun 1.4.3 | 3.440 | 34.089 | 3.270 |

Node 24 and Node 26 SDK and startup ranges overlap. Bun improves startup more than test execution. The MCP loop shares a process with its client, and profiling attributes 62.6% of sample ticks to stacks with a client ancestor. It therefore cannot establish production gateway latency or throughput. Network transport, gateway authentication, upstream API latency, concurrency, and configured telemetry are excluded.

All 54 runtime samples passed their workload and actual-worker runtime assertions. The Bun compatibility rerun on this snapshot still failed one MCP telemetry test and six CLI exit-code tests, so this change does not adopt Bun as the runtime.

## Dependency materialization observations

Each manager ran five rotating cold-cache and five warm-cache samples with a fresh dependency tree each time. Lifecycle scripts were disabled on every side. Both Node versions used the same npm 11.19.1 CLI to isolate runtime effects.

| Installer | Cold package cache, median seconds | Warm package cache, median seconds |
| --- | ---: | ---: |
| npm on Node 24 | 5.2261 | 3.9866 |
| npm on Node 26 | 5.0259 | 3.8836 |
| Bun | 0.5177 | 0.1641 |

All 30 final samples preserved unique package versions and the npm lock hash. A separate workspace-aware check found the same 577 resolved dependency edges, allowing physical deduplication. An earlier root-only inventory check was incomplete and is excluded.

These numbers measure dependency materialization with scripts disabled, not a complete CI install. A separate frozen install with `--no-save` still created a `bun.lock`. No installer or lockfile migration is included.

## Method and evidence

The experiment used one isolated Ubuntu 26.04 amd64 sandbox with 4 vCPUs and 8 GiB RAM. Runtime downloads matched official SHA256 manifests. Timed workloads ran serially with alternating or rotating order. Warmups were excluded. Package caches were explicitly cold or warm; OS and shared network caches were not purged. Every accepted run completed its expected work successfully.

Commands used public source and synthetic fixtures, no application credentials, restricted network access, isolated HOME directories, and disabled live API smoke tests. Runtime comparisons verified actual worker runtimes and unchanged source, dependency-lock, and compiled-code hashes. The sandbox has been stopped.

[Machine-readable results](2026-10-21.json) include every accepted full-suite and install sample, runtime medians and ranges, test counts, and dependency-equivalence checks. Full logs, CPU profiles, experimental harnesses, and independent review records are retained locally; they are not published in this repository.
